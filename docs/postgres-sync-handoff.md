# Postgres sync (Option B) — handoff

State of the DuckLake-mirror → partisipa Postgres sync as of the autonomous
session. Everything below is committed to `mdb-ducklake`.

## What exists

Three CLI commands (console scripts), all driven by a mapping artifact:
- `mdb-ducklake-validate` — read-only reconcile (row counts, PK-set diffs, `--deep` changed rows).
- `mdb-ducklake-to-postgres` — set-based upsert (DuckDB streams Parquet → PG staging, one transaction of `INSERT … ON CONFLICT DO UPDATE`, change-filtered).
- `mdb-ducklake-prune` — guarded delete of rows gone from the mirror (dry-run default).

Mapping artifact: `spikes/mapping/ducklake_pg_mapping.json`, generated by
partisipa's `manage.py dump_ducklake_mapping` (command written to
`partisipa-import/backend/pnds_data/management/commands/`, **uncommitted there**).

## What was validated (real-FK shadow run)

Against `shadow_db` — an isolated database in the `partisipa-agent-oracle` pod
loaded with a schema-only dump of `pnds_data` **including its real FK
constraints** (13, all DEFERRABLE INITIALLY DEFERRED):
- Full sync of 85 tables: stage ~23s + upsert ~2–4s.
- `validate --deep`: **85 clean, 0 differences** after a sync.
- **0 FK orphans** in the mirror data (sampled) — mirror is FK-consistent.
- Prune of a parent+child pair deletes both (reverse-FK order); empty-mirror and
  fraction guards both verified.
- Change-filter: re-syncing an already-current schema writes **0 rows**.

## Key findings / decisions

1. **Materialized views are partisipa's concern — bracket the sync with dbsamizdat.**
   The `pnds_data` schema has dbsamizdat-managed matviews; **11 of 13 read tables
   we sync**. Two carry per-write auto-refresh triggers on *our* tables
   (`SubprojectLatestProgress` ← subproject_physical_progress,
   `LegacySubprojectEnriched` ← suco_subproject) whose `REFRESH MATERIALIZED VIEW
   CONCURRENTLY` cannot run inside our bulk transaction. Rather than have the sync
   tool touch triggers, **partisipa brackets the run**:
   `manage.py dbsamizdat nuke` (drop all managed matviews + triggers) → our sync →
   `manage.py dbsamizdat sync` (recreate + refresh in dependency order). The other
   9 matviews have no write-trigger on our tables today, so they already rely on
   this refresh cadence — no regression. The sync tool itself is trigger-agnostic
   (plain deferred-FK transaction).
2. **Matview inventory** (which read our synced tables): pure-ours —
   `SubprojectLatestProgress`, `CorrectedOutputs`, `SubprojectSubSectorView`,
   `ida_activeprojects`, `ida_districtbudget`, `ida_sucobudget`,
   `ida_projects_per_suco_mv`, `ida_projectcountbysucostatussubsector`; mixed with
   IDA data — `LegacySubprojectEnriched`, `ida_sucomonthlyreport`,
   `ida_districtmonthlyreport`; unaffected — `IdaProjectInfo`,
   `form_submission_…tf611`.
3. **Column mapping** is authoritative from partisipa's models (pydantic alias →
   `db_column`), not a `lower()` guess — needed for the `SubpojectOutputs` typo
   case and irregular FK columns.
4. **`1900-01-00` → NULL** (D4); the mirror keeps the original in `_mdb_cast_rejects`.

## Production run sequence

```
partisipa:  manage.py dbsamizdat nuke        # drop managed matviews + triggers
mdb-ducklake-to-postgres                     # bulk upsert (no triggers to conflict)
mdb-ducklake-prune --apply                   # optional: delete rows gone from mirror
partisipa:  manage.py dbsamizdat sync        # recreate + refresh matviews, in dep order
```

## Before production

- [ ] **Wire the dbsamizdat nuke/sync bracket** into the surrounding job (partisipa
      side). Mind the window: matviews don't exist between `nuke` and `sync`, so
      run off-peak (Metabase cards on them would error meanwhile).
- [ ] **Canonical mapping from partisipa `main`** — the current artifact came from
      the `oracle` feature-branch pod. Regenerate and commit the generator in
      `partisipa-import`.
- [ ] **Single all-or-nothing transaction:** one bad row (e.g. an FK orphan) rolls
      back the whole sync. The mirror was FK-consistent here; revisit if that changes.
- [x] **Parity gate vs the ORM importer — DONE (representative subset).** Loaded
      the same `.accdb` via the ORM importer into an isolated `parity_orm` (FKs
      dropped to isolate value parity from the ORM's per-row FK-skip semantics)
      and `validate --deep`'d the mirror against it for 6 representative tables
      (zsuco, suco_subproject, suco_operational_report, monthly_reports,
      subproject_physical_progress, finance_monitoring). Result: **identical row
      counts; the only value differences are the 8 intentional `1900-01-00`→NULL
      cells** (D4). Full-table-set parity is the remaining confirmation.
      - **Found + fixed a currency-rounding bug:** Access Currency/Double values
        mapped to `integer` partisipa columns were *rounded* by DuckDB's cast but
        *truncated* by the ORM's `int()`, giving off-by-one on ~360 financial
        cells. `mapped_projection` now truncates toward zero for fractional→int
        targets, matching the ORM. (Two behaviours differed; we chose to match
        partisipa's existing values — revisit if rounding is actually preferred.)
- [ ] Optional: skip unchanged *tables* entirely using the mirror's fingerprints
      (currently every table is staged every run).

## Running against a real target

```bash
# creds via env; S3 via sops. PGDATABASE/PGHOST/PGPORT/PGUSER/PGPASSWORD select the target.
sops exec-env s3.enc.env "PGPASSWORD=… PGHOST=… PGPORT=… PGDATABASE=… \
  uv run mdb-ducklake-validate    --mapping spikes/mapping/ducklake_pg_mapping.json"   # dry look
sops exec-env s3.enc.env "PGPASSWORD=… … uv run mdb-ducklake-to-postgres --mapping … " # upsert
# then REFRESH MATERIALIZED VIEW …;  and, if desired:
sops exec-env s3.enc.env "PGPASSWORD=… … uv run mdb-ducklake-prune       --mapping … --apply"
```

The shadow_db used for validation was dropped at end of session.
