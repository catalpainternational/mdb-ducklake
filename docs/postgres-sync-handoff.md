# Postgres sync (Option B) — handoff

State of the DuckLake-mirror → partisipa Postgres sync as of the autonomous
session. Everything below is committed to `mdb-ducklake`.

## What exists

Three CLI commands (console scripts), all driven by a mapping artifact:
- `mdb-ducklake-validate` — read-only reconcile (row counts, PK-set diffs, `--deep` changed rows).
- `mdb-ducklake-to-postgres` — set-based upsert (DuckDB streams Parquet → PG staging, one transaction of `INSERT … ON CONFLICT DO UPDATE`, change-filtered).
- `mdb-ducklake-prune` — guarded delete of rows gone from the mirror (dry-run default).

Mapping artifact: `spikes/mapping/ducklake_pg_mapping.json`, generated by
partisipa's `manage.py dump_ducklake_mapping` (command written to
`partisipa-import/backend/pnds_data/management/commands/`, **uncommitted there**).

## What was validated (real-FK shadow run)

Against `shadow_db` — an isolated database in the `partisipa-agent-oracle` pod
loaded with a schema-only dump of `pnds_data` **including its real FK
constraints** (13, all DEFERRABLE INITIALLY DEFERRED):
- Full sync of 85 tables: stage ~23s + upsert ~2–4s.
- `validate --deep`: **85 clean, 0 differences** after a sync.
- **0 FK orphans** in the mirror data (sampled) — mirror is FK-consistent.
- Prune of a parent+child pair deletes both (reverse-FK order); empty-mirror and
  fraction guards both verified.
- Change-filter: re-syncing an already-current schema writes **0 rows**.

## Key findings / decisions

1. **Materialized-view-refresh trigger.** A `pnds_data` table has a trigger that
   does `REFRESH MATERIALIZED VIEW CONCURRENTLY "SubprojectLatestProgress"` on
   write (at least on the `oracle` branch). It breaks/slows a bulk load. The
   sync therefore runs the load connection in `session_replication_role =
   replica` (superuser), disabling **user triggers and FK enforcement** during
   the bulk write — the mirror loads faithfully and fast — with a fallback to
   deferred-constraints if not superuser. **Consequence: matviews are stale after
   a sync and must be refreshed out of band** (`REFRESH MATERIALIZED VIEW …`).
2. **Column mapping** is authoritative from partisipa's models (pydantic alias →
   `db_column`), not a `lower()` guess — needed for the `SubpojectOutputs` typo
   case and irregular FK columns.
3. **`1900-01-00` → NULL** (D4); the mirror keeps the original in `_mdb_cast_rejects`.

## Before production

- [ ] **Refresh matviews after each sync** (add a `--refresh-matviews` step, or run
      it in the surrounding job). Currently a documented manual step.
- [ ] **Canonical mapping from partisipa `main`** — the current artifact came from
      the `oracle` feature-branch pod. Regenerate and commit the generator in
      `partisipa-import`.
- [ ] **`replica` mode needs a superuser/replication role** on the target. Confirm
      the production sync role qualifies, or accept the deferred-constraints
      fallback (triggers then fire — beware the matview trigger).
- [ ] **Single all-or-nothing transaction:** one bad row rolls back the whole sync.
      The mirror was FK-consistent here; revisit if that ever changes.
- [ ] **Parity gate vs the ORM importer** — not run this session. Load the *same*
      `.accdb` via `manage.py import_from_accessdb` into a fresh DB and
      `validate --deep` our output against it to quantify any residual differences
      (expected: only the `1900-01-00`→NULL cells and TRY_CAST rejects).
- [ ] Optional: skip unchanged *tables* entirely using the mirror's fingerprints
      (currently every table is staged every run).

## Running against a real target

```bash
# creds via env; S3 via sops. PGDATABASE/PGHOST/PGPORT/PGUSER/PGPASSWORD select the target.
sops exec-env s3.enc.env "PGPASSWORD=… PGHOST=… PGPORT=… PGDATABASE=… \
  uv run mdb-ducklake-validate    --mapping spikes/mapping/ducklake_pg_mapping.json"   # dry look
sops exec-env s3.enc.env "PGPASSWORD=… … uv run mdb-ducklake-to-postgres --mapping … " # upsert
# then REFRESH MATERIALIZED VIEW …;  and, if desired:
sops exec-env s3.enc.env "PGPASSWORD=… … uv run mdb-ducklake-prune       --mapping … --apply"
```

The shadow_db used for validation was dropped at end of session.
